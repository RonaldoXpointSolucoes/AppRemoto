# Automatic Windows installation and one-click access

User request: replace the exhausting six-step manual procedure with a Windows installer that configures RustDesk, enrolls the customer PC, starts unattended operation on boot, and exposes a Connect action in the existing panel.

## Product flow

The authenticated Setup page asks only for customer organization and device name. Generate installation creates a 30-minute single-use organization-scoped enrollment token and downloads one personalized Windows x64 EXE. The customer double-clicks it and approves the normal administrator prompt. The installer configures the existing XPoint RustDesk server, installs RustDesk if missing, enrolls through the existing API, sets the server-generated permanent unique password, and starts a Windows service. No terminal commands or manual server/password entry are required. The panel waits for the enrollment receipt and current heartbeat, then shows the matching device. Connect opens the local RustDesk handler on an authorized technician workstation; an OS/browser handler confirmation cannot be bypassed.

## Boundaries

- Reuse current Appwrite schema, enrollment transactions, encrypted device_credentials and audit_logs. No new collections or master keys.
- POST /v1/enrollment-tokens requires canManageDevices for an active organization. Request {organizationId, deviceDisplayName}; response {enrollmentId,enrollmentToken,expiresAt}. Store only hash, one use,30-minute expiry and creator. Audit before returning. No-store responses, generic errors and no credentials in logs.
- GET /v1/enrollment-tokens/:enrollmentId/status requires canManageDevices for its organization. Response {status:'waiting'|'online'|'offline',expiresAt,device:DeviceView|null}. Match the committed receipt for this token, never by display name alone.
- POST /v1/devices/:deviceId/connect requires current canConnect and enabled, ONLINE device. Return {launchUri} with rustdesk protocol only after credential lookup/decryption and successful audit. Include approved self-host server/public key. The browser launches transiently; never store/render/log the URI or secret password. It is a privileged connection launch, not proof of a completed remote session.
- Existing short-lived enrollment/device credentials stay out of Git, logs, URLs, filenames and visible UI. The downloaded personalized installer contains its one-time provisioning token; sharing it authorizes one enrollment into that customer before expiry.

## Native installer and service

Build a Go Windows x64 setup executable from the existing services/agent module. Personalization uses a bounded PE overlay: UTF-8 JSON {schemaVersion:1,enrollmentId,enrollmentToken,expiresAt,organizationId,deviceDisplayName}, followed by uint32 little-endian JSON length and ASCII XPOINT_SETUP_V1. Maximum JSON16KiB, strict fields and validation. No configurable executable or API destinations in the overlay. A reviewed fixed HTTPS API, public RustDesk host/key and pinned official RustDesk binary SHA256 are compiled into the release. Distribution manifest includes version, baseEXE path and SHA256. Browser validates the base artifact before appending provisioning data.

The installer elevates normally, installs into trusted Program Files and ProgramData locations and rejects untrusted/reparse targets. Enrollment/device tokens never enter arguments. Verified upstream compatibility exception: the permanent password briefly enters the supported RustDesk --password command under the hardened SYSTEM runner; privileged administrators can inspect it. Do not log arguments/output. RustDesk 1.4.9 rejects foreign IPC peers; do not bypass that policy or replace private identity through full configuration import. It copies a clean runtime executable without the provisioning overlay. Use a clearly named Windows service XPointRemoteAgent, automatic start and recovery, running as LocalSystem. Enrollment and steady-state agent DPAPI use the same SYSTEM account; bootstrap handoff is machine-DPAPI-protected with SYSTEM/Administrators-only ACLs and removed after confirmed consumption. Keep existing manual current-user state separate. Never delete pending state or replace identities after an uncertain enrollment.

RustDesk must use official pinned distribution with verified SHA256. Apply public server configuration using supported CLI; permanent password is generated uniquely by the existing enrollment service. Preserve unrelated RustDesk settings and do not silently overwrite an existing managed XPoint installation into another customer. Setup succeeds only after service startup and a confirmed API heartbeat. A failure gives a concise stage/error code, preserves recovery state and does not report success. Provide explicit uninstall for XPoint service without deleting shared RustDesk or unrelated applications.

## Verification and publication

Focused backend authorization/no-store/audit/decryption/status tests; agent overlay, installer and service lifecycle tests plus Windows build; panel setup/download/correlation/connect and responsive tests; then production API non-overlapping single-writer deploy and panel deploy. Confirm exact commits and public health. Exercise actual production enrollment with a controlled identity only if a suitable authorized Windows machine is available. Do not describe mocks, compilation, port reachability or UI launch as proof of installation or a remote session. Record any remaining physical-machine validation plainly. Code signing needs an actual signing certificate; do not claim unsigned artifacts are signed.
